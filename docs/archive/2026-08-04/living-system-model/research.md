## Candidate A: Extend the existing store in place

- **Summary**: Keep the seven categories and the sharded shape. Add `governs:` (path anchors) to decision frontmatter, add `constraints` as an eighth category, extend `PHASE_BY_PREFIX` with a path-glob scope vocabulary, and add supersession-awareness to the staleness predicate. Persist a discard ledger so curation survives `/memory-flush`.
- **API references (current)**:
  - Node builtins only — `engines: {"node": ">=18.17.0"}`, `package.json`. Runtime `dependencies` is `["@clack/prompts"]`; everything in `.claude/` is zero-dep by the predecessor's non-goal.
  - MADR status vocabulary — `Proposed / Accepted / Deprecated / Superseded`, with `Superseded by ADR-NNNN` carrying the replacement's id so the chain is traversable forward — [About MADR](https://adr.github.io/madr/), [MADR Template Primer](https://ozimmer.ch/practices/2022/11/22/MADRTemplatePrimer.html)
- **Fits**: Yes. Scout's "Patterns in use here" — logic lives in `.claude/hooks/lib/*.mjs`, readers are presence-based, actuators are deterministic `.mjs` with human curation. Every change lands inside an existing seam: `memory_session_start.mjs:18-20`, `process_lifecycle_guard.mjs:31-37`, `route.mjs:22-26`.
- **Tests it enables**: Direct extension of 28 existing memory test files. `memory-scoped-surface.test.mjs` gains a source-path case; `memory-session-start-head-decay.test.mjs` gains a superseded-entry case; `memory-stop-dedup.test.mjs` gains a survives-flush case. Real files in temp dirs, no mocks — the existing tests already work this way.
- **Tradeoffs**: Does not give slice E anything — there is still no durable structural corpus, only better decisions. Grows `scope:` into a two-kind vocabulary (phases *and* path globs), which is a schema wart every reader must then handle. Eighth category means touching `CANONICAL` at `memory_session_start.mjs:16` and every consumer that enumerates it.

## Candidate B: Workspace model, Structurizr semantics without the dependency

- **Summary**: Introduce one durable workspace artifact holding model, views, decisions, and constraints together, which each cycle *extends* rather than rewrites. Borrow Structurizr's proven semantics; implement them in zero-dep `.mjs` over plain files.
- **API references (current)**:
  - `workspace extends <file|url> { ... }` — *"A workspace can extend another workspace, allowing for incremental additions to an existing model and views."* — [Structurizr DSL language](https://docs.structurizr.com/dsl/language), [workspace-extension cookbook](https://docs.structurizr.com/dsl/cookbook/workspace-extension)
  - `!adrs` — attaches ADRs in Markdown/AsciiDoc *to the workspace, software system, or container context* — [Structurizr DSL language](https://docs.structurizr.com/dsl/language)
  - *"A workspace serves as a container for a software architecture model... It also holds views... as well as Markdown or AsciiDoc documentation and architecture decision records."* — [Structurizr workspaces](https://docs.structurizr.com/workspaces); *"A workspace should contain the model, views, documentation, and decisions for a single software system"* — [recommendations](https://docs.structurizr.com/workspaces/recommendations)
- **Fits**: Partly. The *semantics* validate the vision note's three-layer cover externally — a mature tool co-locates model + views + docs + decisions in one evolving container, and anchors ADRs to model elements exactly as slice A's `governs:` proposes. The *implementation* does not fit: Structurizr's model is Java (`/structurizr/java`) plus a CLI, and `plantuml_syntax_guard` is already advisory-by-default in this repo *because there is no JVM*. Adopting the tool violates the predecessor's zero-dep non-goal; adopting the pattern does not.
- **Tests it enables**: Extension/merge semantics are directly testable — extend a base workspace twice from disjoint slices, assert both contributions survive. This is the only candidate that gives slice E's merge-semantics AC a testable shape.
- **Tradeoffs**: Largest blast radius by far. Creates a second home for structural truth alongside `.claude/project.json → artifacts.required_diagrams.spec` and `.claude/skills/spec/template.md` — the three-way drift scout flagged. Nothing in the repo has this shape today, so there is no seam to extend and no prior test to inherit. Re-implementing `extends` resolution correctly is real work that YAGNI would question until slice E is actually committed.

## Candidate C: Derived read-layer index, regenerated not stored

- **Summary**: Leave all storage exactly as it is. Build an index that is *derived* from the shards on demand (or at session start), holding only the reverse lookups: path→decisions, component→diagrams, constraint→dependent decisions. Nothing new is persisted as truth; the index is a cache with a rebuild command.
- **API references (current)**: Node builtins; existing `frontmatter-parser.mjs:34,41` (`parseFrontmatter`, `asArray`) is already the shard reader every consumer goes through, and `.claude/skills/memory-index/migrate.mjs` establishes the index-tooling location.
- **Fits**: Yes, and better than it did in July. This is the alternative the predecessor rejected for the 500-cap problem, which sharding solved. Derivation also sidesteps the honesty hazard the intake names: a derived index cannot drift from its source, because it *is* its source, re-read.
- **Tests it enables**: Purely functional — given a fixture shard directory, assert the index resolves each reverse lookup. No state, no fixtures beyond files, trivially deterministic.
- **Tradeoffs**: Answers *retrieval* but not *representation*. A derived index cannot invent the `governs:` anchors or the constraint nodes it would index — those must exist first (Candidate A). So C is not an alternative to A; it is the layer above it. Rebuild cost is unmeasured, though the corpus is 226 entries, so this is very likely negligible.

## Recommendation

**A for the node model, C for the index; defer B's implementation to slice E's own cycle while adopting its semantics as the design target.**

Reasoning against the intake's stated primary success signal ("reasons reach you unprompted", which ordered slices A and C ahead of E): A and C together are exactly what that signal needs, and both land inside seams that already exist and are already tested. B is the right long-term shape and is externally validated, but it is the only candidate with no seam to extend, and it serves the slice already flagged oversized at triage.

Note that A and C are complements, not rivals — C cannot index anchors that A has not created. The real fork is **B now vs. B later**.

**What would flip this**: if `/spec` concludes slice E belongs in this epic rather than its own, B becomes load-bearing immediately, and A and C should then be designed to live *inside* a workspace model rather than beside it — retrofitting that later would be a rewrite, not an extension. The deciding question is slice E's sizing, which is already an open question at triage.

## Open questions

Questions a human reviewer must decide before the spec is written:

1. **The scope-tag backfill deferred on 2026-07-17 is now due.** Its own words: *"resolve before the surfacing slice implements"*. Do the 191 migrated facts default to their category's owning phase, or to `scope: any`? This decides whether slice C changes a vocabulary or backfills a corpus.
2. **Is `scope:` extended to carry path globs, or does edit-time surfacing get a second trigger keyed on path?** Extending `scope:` gives one vocabulary two kinds; a second trigger keeps them clean but adds a code path. Scout flagged this as the largest unknown in slice C.
3. **Is `constraint` an eighth canonical category, a property on existing entries, or a derived view?** Vision §3.4 left this open and noted each implies a different index. Candidate A assumes the first.
4. **Does `governs:` anchor to path globs or to `path:line`?** `landmines.md` uses `path:line` and it drifts; globs survive refactors but resolve coarsely.
5. **Slice E: one child, or its own epic?** This is the fork that decides B-now vs B-later, so it should be settled before the sliced spec is written rather than at implementation.
6. **Does MADR's full status lifecycle (`Proposed / Accepted / Deprecated / Superseded`) get adopted, or only `Superseded`?** The repo has `superseded-at:` already; the rest of the lifecycle is new surface that nothing currently needs.
