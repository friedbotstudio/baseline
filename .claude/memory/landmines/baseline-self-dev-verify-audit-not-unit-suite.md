- **RE-VERIFIED 2026-08-17 — the core trap below is RESOLVED, and the outcome recurred anyway.** `project.json → test.cmd` is now `node .claude/skills/audit-baseline/audit.mjs --file={file} && node --test tests/*.test.mjs`: the "or makes `test.cmd` run both" fix this entry proposed was taken, so the binding stamp DOES observe the unit suite. Do not act on the audit-only premise below; it describes a configuration that no longer exists. Kept for the casualty record and because the diagnosis order still holds.
- **And yet `309d70e` landed with two red unit tests under a `PASS` stamp, exactly as `79e41cb` did.** Same outcome, different mechanism: the verify no longer misses the suite, it runs *before the state that breaks it exists*. See [[a-binding-pass-stamp-goes-stale-before-the-commit-it-authorises]] for both doors. The lesson that survives is narrower than this entry's title: a green stamp is evidence about the tree **at stamp time**, never about the commit.

- Path: `.claude/project.json → test.cmd` = `node .claude/skills/audit-baseline/audit.mjs --file={file}` (`test.kind: structural`) vs `package.json → scripts.test` = `node --test --test-reporter=spec tests/*.test.mjs`.
- Trap: when developing the baseline ON the baseline, the BINDING verification (`verify-tick`, `/simplify` re-verify, `/integrate`) runs `test.cmd` = the STRUCTURAL AUDIT, not the unit suite. The `node --test tests/*.test.mjs` unit suite is a SEPARATE command (`npm test`); `/implement`'s RALPH loop drives the specific failing tests via `node --test <file>`, but no workflow phase runs the FULL unit suite as its binding stamp. So a change can pass every phase's audit and still have BROKEN UNIT TESTS no phase caught — and several unit tests inspect baseline SKILL.md bodies (`tier-dial-coverage.test.mjs` reads `simplify`/`security`/`spec-lint`/`integrate` SKILL.md for the tier-dial read-path line), so editing a checker skill can break a unit test the structural audit is blind to.
- **CONFIRMED WITH A CASUALTY, 2026-08-13.** This stopped being a risk and became a shipped defect: commit `79e41cb` landed with TWO red unit tests under a `PASS` stamp — `test_when_landmark_scope_counted_...` (literal 87, actual 88) and `test_when_phase_budgets_measured_...` (spec 67 over a 65 cap). Every phase of that workflow was green because every phase stamped the audit. The failures surfaced only when the NEXT workflow ran `npm test` by hand. The 2026-06-22 mitigation below (run it manually as well) is what failed: a manual step outside the stamp is a step that gets skipped, and nothing on disk records that it was.
- **Stronger mitigation, used through `diagram-shard-rewrite-loses-fields`:** stamp `.claude/state/last_test_result` from the command that actually ran the suite, and put that command on line 3. The statefile IS the verdict, so a PASS whose line 3 names a command that cannot observe a failure is not a verdict. This is a deviation from the verify contract's "read `test.cmd`, run it" — take it knowingly, and say so in the phase report.
- **It is not a typo, which is why it survives review.** `--file={file}` was authored for the `test_runner` PostToolUse hook, which substitutes the edited path per write; the same key doubles as the verify command with the placeholder stripped. One value serves two consumers, and the verify consumer is the one that silently loses. A real fix splits the keys (a per-file `test.file_cmd` for the hook, a full-suite `test.cmd` for verify) or makes `test.cmd` run both — do NOT point `test.cmd` at `npm test` alone, since the audit is a real gate and the hook needs its per-file form.
- Mitigation (2026-06-22, superseded by the stamp rule above but still worth doing): for any change that edits a baseline skill/hook body or adds a helper under `.claude/skills/<slug>/`, run `npm test` MANUALLY during `/integrate` (in addition to the binding audit stamp) — the audit is necessary but not sufficient. Run it serially for a deterministic verdict (`node --test --test-concurrency=1 tests/*.test.mjs`) per [[live-objtemplate-rebuild-races]]. The unit suite is also the only place a NEW unit test (e.g. a helper's own tests) actually executes inside the workflow.
