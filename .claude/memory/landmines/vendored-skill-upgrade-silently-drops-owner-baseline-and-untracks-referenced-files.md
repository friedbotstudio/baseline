- **A vendored-skill upgrade can drop the skill out of the baseline roster without anyone adding or removing a skill.** Art. XII makes a skill baseline-owned *iff* its `SKILL.md` frontmatter declares `owner: baseline`, and a missing `owner:` is **silently skipped** (the only frontmatter FAIL is a present-but-malformed value). An upstream drop that overwrites `SKILL.md` wholesale takes the annotation with it. On 2026-07-26 `impeccable` v3.5.0 → v4.0.2 removed the `owner: baseline` line and deleted `LICENSE` + `NOTICE`; disk went 52 → 51 with no skill added or removed.
- **The failure surfaces far from its cause.** `audit-baseline` reported seven FAILs at once: `skills count (seed vs baseline)` (seed claims 52, disk has 51), `skills names match seed §4.3` (missing `impeccable`), two `baseline skill missing` rows for the deleted licence files, a `hash mismatch`, `docs/init/seed.md count claims`, and `byCategory sum 52 != skills total 51`. The site rendered the contradiction publicly: `/skills/core/` said "ships 51 skills" above section headings summing to 52, because `skills.total` derives from disk while `SKILL_CATEGORIES` in `derive-counts.mjs` is a hand-maintained literal. `tests/standup-site.test.mjs` failed on audit neutrality. **None of these name the real cause.** Restoring one frontmatter line cleared all seven.
- **Second, worse half: files the upgrade ADDS are untracked, and a baseline-owned skill ships from a clean checkout.** The same drop left six `reference/*.md` files that `SKILL.md` loads (`craft-floor`, `new-work`, `operate`, `routing`, `doctor`, `hooks`) on disk but never `git add`ed. Every local gate passed — `npm pack`, `publish:check`, `publish:smoke`, `scan-shipped-skills` — because they all read the **working tree**. CI publishes from a **git checkout**. Prove it with `git archive HEAD | tar t | grep <path>`: the files were absent, so `prepack` would have built a template whose `SKILL.md` says "load `reference/routing.md`" against a file that does not exist. The smoke test cannot catch this: it verifies the manifest matches the tree, not that `SKILL.md`'s references resolve.
- **Mitigation, in this order.** (1) After any vendored-skill bump, `grep -c "^owner: baseline" .claude/skills/*/SKILL.md` and compare against the expected roster count. (2) `git status --porcelain .claude/skills/<slug>` and stage every addition and deletion — a partially-staged vendor drop is the default outcome, not an edge case. (3) Resolve every path the new `SKILL.md` names against the **index**, not the worktree: `for p in $(git show :.../SKILL.md | grep -ohE '(reference|scripts)/[a-z-]+\.(md|mjs)'); do git cat-file -e ":.../$p" || echo MISSING $p; done`. (4) Only then `npm run build` and `audit-baseline`.
- **Do not diagnose this from the count alone.** The count drift looks identical to [[baseline-skill-count-cascade]] (the deliberate add/remove case) but has the opposite fix: there, you sweep every prose surface to match the new count; here, you restore one line so the count goes back. Reading the cascade landmine first will send you to edit `seed.md` and the site copy, which is exactly wrong.
- **Related:** the manifest-only build path does not prune. `scripts/build-template.sh:119`'s `rm -rf "$TEMPLATE_DIR"` sits inside the block `--manifest-only` skips, so `npm run manifest:refresh` overlays onto the existing template and leaves files deleted upstream in place (here, four `reference/*.md` the upgrade removed). It cannot reach a published artifact — `prepack` runs the full build — but it corrupts `obj/template` locally and makes the audit read as broken. `npm run build` clears it.
