- Decision: adopt Structurizr's **semantics** as the design target for the durable architecture workspace; reject Structurizr itself as a dependency. Specifically adopted: `workspace extends <file|url>` (incremental contribution to an existing model rather than a rewrite) and `!adrs` (decision records anchored to a model element rather than floating free). Implemented in zero-dep `.mjs` over plain files.
- Rationale: Structurizr independently validates the three-layer cover the vision note derived — its docs state that "a workspace should contain the model, views, documentation, and decisions for a single software system." That is external confirmation that model + decisions + views belong in one evolving container, which is the whole premise of the epic. But the tool is JVM-based (`/structurizr/java` plus a CLI), and the predecessor cycle's standing non-goal forbids "any runtime dependency or external graph database — store and index stay plain files, generated by zero-dep `.mjs` (Node builtins only)". `plantuml_syntax_guard` is already advisory-by-default in this repo precisely *because* there is no JVM, so a JVM dependency would be a new class of requirement, not an incremental one.
- Rejected alternatives:
  - Adopt Structurizr as a real dependency → JVM plus runtime dep; violates the standing zero-dep non-goal, and the repo has no JVM (see `plantuml_syntax_guard`'s advisory default).
  - Ignore the prior art and derive the contribution model from scratch → discards a proven `extends` design and a proven element-anchored ADR model for no benefit; Article VI.5 requires checking current docs before writing against an external API, and doing so surfaced both mechanisms.
  - File this under `libraries.md` → wrong register. Structurizr is deliberately NOT a project dependency; it appears in no lockfile, so there is no version to pin, and a libraries entry would misrepresent it as something the build consumes.
- Load-bearing: yes. If a future slice re-proposes vendoring Structurizr (or any model tool with a runtime), the rejection reason above is the reason it does not land. The zero-dep constraint is inherited, not local to this epic.
- Consumers: slice E (workspace corpus) treats `extends` as the contribution mechanism; slice A treats `!adrs` element-anchoring as the precedent for `governs:`.
